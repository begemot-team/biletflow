# Нурсат — шестой этап, финальная сдача

Подготовлено 20 ноября 2026 года. Ветки: `codex/nursat-phase6` (замеры и
документация), `codex/mobile-api-fixes` (мобильный сканер).

Шестой этап — стабилизация перед финальной сдачей. План: разбор багов, замеры
производительности checkout и проверки QR, документация по развёртыванию,
помощь с репетицией демо. Плюс хвосты из отчёта Phase 5: обновить `main` и
подключить мобильный сканер к API.

## Результат

- **`main` обновлён для сдачи (PR #30).** `main` не менялся с 9 сентября, а в `dev`
  накопилось 106 коммитов (фазы 2–6 всей команды). Перед мержем `dev` проверен
  целиком: бэкенд — 131 тест, `ruff` и проверка миграций чистые, `demo_mvp.py`
  проходит; фронтенд — 55 тестов, lint, сборка; CI на PR зелёный. В `main` не
  было коммитов, которых нет в `dev`, поэтому мерж прошёл без конфликтов.
- **Автодеплой (PR #29, затем на `main`).** Каждый merge в `main` сам выкладывается
  на Heroku (https://begemot-b8b43e7ea8ea.herokuapp.com) и проверяет `/api/health`.
  Живой сайт показывает то, что сдано, а не промежуточное состояние `dev`. При
  ошибке сборки или миграции продолжает работать прошлая версия.
- **Мобильный сканер подключён к API (PR #31, ждёт ревью Абылая).** Запросы
  мобильного приложения повторены через curl против Docker Compose; бэкенд
  соответствует контракту, расхождения были в `mobile/`:

  | Запрос | Было | Стало |
  | --- | --- | --- |
  | Вход `{email, username, password}` | 400, лишнее поле | `{email, password}` → 200, токен `access` сохраняется |
  | `POST /tickets/verify/`, `/tickets/check-in/` | 404 из-за слэша в конце | без слэша → 200, повторный скан 409 |
  | `GET /events/:id/attendees/` | 404, на экране 3 выдуманных посетителя | список с пагинацией читается |

  Ещё: статус `checked_in` вместо `used`. Ручной check-in из списка теперь шлёт
  `qr_token` билета, а не `identifier`. При отказе сервера экран больше не
  отмечает билет «прошедшим», а показывает ошибку («Ticket has already been
  checked in.»). Мобильные тесты: 17 (3 новых).
- **Замеры производительности.** Новый `bench_checkout.py` рядом с
  `bench_checkin.py`. Gunicorn с 3 воркерами, как на Heroku:

  | Сценарий | p50 | p95 | max |
  | --- | --- | --- | --- |
  | Резерв + оплата (100 заказов) | 20.5 мс | 23.5 мс | 69.9 мс |
  | Сканер: verify + check-in (200 билетов) | 11.6 мс | 14.3 мс | 30.3 мс |

  Требование SRS — проход за ~2 с, запас на два порядка. Конкурентный прогон:
  40 одновременных покупок на 10 билетов — продано ровно 10, 30 получили отказ,
  двойной продажи нет.
- **Документация по развёртыванию** — `docs/DEPLOYMENT.md`: локальный Compose и
  Heroku в одной таблице, config vars (проверены по живому приложению), автодеплой,
  откат, ручной деплой через Container Registry (когда `git push heroku` не
  работает с git из Xcode), как направить мобильный сканер на Heroku, проверка после
  деплоя и как повторить замеры. README ссылается на документ.

## Демо на финальной сдаче

1. Открыть https://begemot-b8b43e7ea8ea.herokuapp.com (или локально:
   `docker compose up --build -d --wait` → `seed_demo` → `localhost:5173`).
2. Организатор: создать событие, тип билета, промокод; для платного — пройти
   активацию продаж.
3. Посетитель: применить промокод, оплатить (симуляция), получить QR-билет с
   именем владельца, PDF.
4. Сканер (мобильное приложение или `POST /api/tickets/check-in`): первый проход
   принят, повторный — 409.
5. Админка `/admin`: пользователи, события, активации, аналитика события.
6. Возврат заказа на странице продаж организатора (после мержа #23).
